## Failures

### A1 / C1 — Claude AI-response extraction is broken (live data loss, not just canary)

**This is one root cause surfacing in two places** — the selector-health canary (A1) and a real
Pro-tier port (C1) — so they're reported together.

**Root cause**: `src/content.js` defines `AI_CLASS_FRAGMENT = 'font-claude-response'` (line 38)
and both `findAiTurns()` (line 491-492, the function the live extraction path uses to locate
Claude's AI responses) and the file-attachment turn-role logic (line 432) key off
`[class*="font-claude-response"]`. That class fragment **no longer exists anywhere in Claude's
current DOM** (confirmed via full-page scan: 0 matches). Claude's assistant-message container now
exposes `data-testid="assistant-message"` instead:
```html
<div data-cds="AssistantMessage" class="group/message-row relative flex w-full min-w-0 flex-col gap-xs break-words select-text print:block" data-testid="assistant-message" data-turn-key="01a0dffb-4aed-7619-baa1-d2da75bd6cef-hub-reply" data-is-streaming="false"><h2 data-find-omitted="" class="sr-only select-none">Claude responded: I can't build an accurate 3D model from these photos.</h2> ...
```
Remote-config override was checked first and is not currently compensating:
`window.PortilityConfig.getRemoteSelectors('claude')` → `null`.

**A1 (canary) — Expected**: human-turn count > 0, AI-turn count > 0, roughly equal to visible
turns. **Actual**: human count = 1 (correct selector), AI count = **0**.
Conversation tested: `https://claude.ai/chat/fb59fa0d-1ee1-400a-9c38-ff4e98f493d3`.

**C1 (live Pro port, Claude → Gemini) — Expected**: ported brief contains the full conversation
(human + AI turns) plus selected images. **Actual**: the ported brief pasted into the new Gemini
chat ends immediately after the human's message —
`"Human: Use these images to create a 3-D model of my head"` — with **zero text from Claude's
actual 8-step photogrammetry-guide response**, even though that response was clearly visible and
substantial in the source conversation (confirmed via screenshot before porting). The 3 images and
the user's profile brief *did* port correctly, and the extraction didn't error or hang — it just
silently omitted every AI turn. From a user's perspective this looks like a successful port with
no error shown, but the destination AI is missing all of the original assistant's reasoning/output,
which is likely to produce confused or wrong responses in the destination chat and is a trust-
damaging silent data-loss bug, not a cosmetic one.

**Impact**: this affects every "Port My Chat" / "Port My Chat Pro" operation sourced from Claude,
for every user, right now — not a theoretical regression. Fixing `AI_CLASS_FRAGMENT` (or switching
to `[data-testid="assistant-message"]`) in `src/content.js` should restore both the canary and the
live flow simultaneously, since they share the one root selector constant.

**Evidence**:
- outerHTML of the real assistant-message container (A1), full-DOM class-fragment scan returning 0
  matches for `font-claude-response`.
- Full `innerText` dump of the actual pasted Gemini brief (C1), captured post-port, showing the
  text cuts off after the human turn.
- Screenshot of the source Claude conversation showing the AI response was present and substantial
  before the port ran.
- Console messages on the Claude tab: no Portility-origin errors logged (the `[log] "Not on Claude
  page"` message present is unrelated — not from this repo).

## Fix Verification

Applied fix: `src/content.js` — `AI_TESTID_SELECTOR = '[data-testid="assistant-message"]'` added
and unioned into every place the old `[class*="font-claude-response"]`-only selector was used
(`aiTurnSelector()`, used by `findAiTurns()`, `siblingIsAnotherTurn()`, and the file-attachment
turn-role check); `content-shared.js`'s cross-platform sibling turn-boundary check also updated.
Extension reloaded, then re-tested against the same conversation
(`https://claude.ai/chat/fb59fa0d-1ee1-400a-9c38-ff4e98f493d3`):

- **A1 re-run**: `document.querySelectorAll('[data-testid="assistant-message"], [class*="font-claude-response"]')` → 1 match (was 0). humanCount=1, aiCount=1 — PASS.
- **C1 re-run** (live Pro port, Claude → Gemini, profile unchecked this time for a cleaner diff):
  the pasted brief now includes the full `Assistant:` turn — all 8 steps of the photogrammetry
  how-to guide are present verbatim, matching the source conversation. Previously this was
  completely absent (cut off right after the `Human:` line).
- **Cosmetic artifact — fixed in a follow-up pass**: the ported `Assistant:` turn was initially
  preceded by two short duplicate lines — Claude's hidden `<h2 class="sr-only">Claude responded:
  …</h2>` accessibility summary and a "thinking status" label ("Assessing the feasibility of
  building a 3D head model from selfies.", doubled) — before the real response text. Root cause:
  `extractElementText()`'s DOM walk in `src/content-shared.js` had no exclusion for either
  element. Both happen to carry `data-find-omitted=""` — Claude's own semantic marker that this is
  UI chrome, not conversation content — so the fix adds one check, `if
  (node.hasAttribute('data-find-omitted')) return '';`, rather than pattern-matching on the
  `sr-only` class or specific label text (which would be fragile and Claude-specific). Re-verified
  with a second live Pro port of the same conversation after reloading: the `Assistant:` turn now
  goes directly into the real response text with no stray lines.
